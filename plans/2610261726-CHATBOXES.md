# Chatboxes on EDW: marketer first, then school support

Operator 10-26: "chatboxes: marketer first, for the website the E is building for Eduweb; then a support
agent for inside eduweb with read-only credentials and access to only one school, structurally."

Builds on the 10-24 design (plans/2610231430-EDW-CONTAINER.md, "the chatbox (limbs.http)"): each chatbox
session is a conversation (a folder under `conversations/http/`), the being answers with memory, replies
stream (SSE) plus a plain JSON reply, "not a Claude proxy".

## Rulings (operator 10-26)
- **The desk is the boundary.** A chatbox conversation's folder is seeded with the files its being may
  use (a copy per conversation). Support gets the school's scoped read-only DB credentials "in a drawer"
  on its desk. "It's structural, all chats are also structurally recorded": every chatbox conversation is
  a normal conversation folder with its transcript.
- **Team view: a Telegram topic per chatbox conversation** in one forum group; the team reads live and
  replies there, and the reply reaches the visitor.
- **No public endpoint by default:** "why not use the private domain? it's all on AWS side". The website's
  server reaches EDW privately. Configurable, for a website hosted elsewhere (then a public HTTPS front).
- **Marketer model: claude-haiku-5-5, effort high** ("we can try").

## Phase 1 — marketer chatbox
1. **limbs.http** (egpt, new limb beside telegram.mjs, through limb-intake): a session token per visitor;
   each session → conversation `http/<client>-<session>`; POST a message, reply as JSON and SSE. Binds a
   configurable private address. Config per client: being, seed folder, mirror group, allowed origins.
   → verify: two browser sessions get two folders and two transcripts; a reply streams.
2. **Seeded desk:** a new chatbox conversation gets a copy of its client's seed folder (identity notes,
   manuals, the site's text). Reuse the room-skeleton copy, no second mechanism.
   → verify: the folder holds the seed on the first message; later seed edits don't touch old chats.
3. **A read-only access level** (4th tier: a file in config/permissions/ + its name in ACCESS_LEVELS):
   Read/Glob/Grep inside its own folder; no Bash, Write, web, Task; no node-wide read grant; no shared
   cards that name internals (pointers, actions).
   → verify: asked to read ../ or src/egpt, or to fetch a URL, the being can't.
4. **Topic mirror:** each chatbox conversation opens a topic in the "EduWeb Chatbox" forum group; visitor
   and being lines appear there; a team member's reply in the topic goes to the visitor.
   → verify: a reply typed in the topic shows in the browser widget.
5. **The marketer being** on EDW: haiku 5.5 high, identity from identidad.md adapted from WhatsApp to the
   website chat, mode on.
6. **Private path** from the website's server to EDW's chatbox port (see "Open").
7. **Widget:** one small JS file + a snippet; ED adds it to the v6 site.
   → verify: on the v6 preview, a visitor chats and the team sees the topic.

## Phase 2 — school support (one pilot school)
1. **DB, structural:** a per-school read-only role that sees only views in its own schema
   (`soporte_<abr>`), each `SELECT … FROM public.<t> WHERE plantel LIKE '<code>.%'` (security_barrier),
   role default read-only + statement_timeout. No change to existing tables or the app. Tables without
   plantel: only global reference tables, or joined to a parent that has it. Built by ED with Jaime on
   the pilot school (suggested: `demoiev`).
   → verify: as that role, every view returns only that school's rows and `public.*` is denied.
2. **Drawer:** the role's credentials seeded into each support conversation's drawer; the being runs at
   `sandbox` (its own Unix user) with psql.
3. **Entry:** the app's foot.inc embeds the widget with a signed token (HMAC: school, user, TipoUsuario)
   → egpt maps it to that school's support client.
4. **Network EDW → Aurora** (the cluster-ro endpoint) over the same private path as phase 1.

## Rulings (operator 10-26, later)
- **Private path, configurable** (a config.yaml block): VPC peering when both ends are on AWS; a scoped SSH tunnel otherwise. The chatbox endpoint for an external website provider is a public HTTPS front, also by config.

## Phase 2 scope — the per-user drawer (operator 10-27: "you can scope the per user drawer, ED is perhaps more in context")
Who sees what is decided by trusted code, never by the being. The being (access level `reader`) can only read its own conversation folder, so the drawer is the only EduWeb data it ever has.
1. **Identity** (feat/chatbox-identity, building): EduWeb's PHP signs `{abrin, user_type, short_name, username, user_id, exp}` with the client's secret, and the widget carries it. egpt verifies it, keeps one conversation per user, titles the topic `{abrin} {user_type} {short_name} ({username})`, and writes `usuario.json` on the desk.
   → verify: a forged or expired token is refused; another user on the same browser gets their own conversation.
2. **The filler (egpt side):** per client, `drawer.command`, run by the spine at session start, after an "end conversation", and when the drawer is older than `drawer.max_age` hours.
   - Env: the verified identity, plus `DRAWER_DIR` = `<conversation>/gavetas/`.
   - It reads its DB credentials from the node's secrets, never from the desk.
   - Timeout, then log; on failure the being gets a one-line `gavetas/ERROR.md` and tells the user it couldn't load their data.
   → verify: the being's folder never contains a credential; a filler failure doesn't block the chat.
3. **The data (ED, with Jaime):** per `tipo_usuario` (R representante, P docente, A alumno, X director, W control de estudio, Z administrador, C colaborador, F familiar, E exalumno, S superusuario), decide which files go in `gavetas/`, each produced by a SQL query filtered by plantel AND the user:
   - a parent's children, their grades, report cards and payments;
   - a teacher's sections and subjects;
   - school-level summaries for staff.
   → verify: for 2–3 test users of demoiev, the drawer contains only their own data.
4. **DB access, structural:** a read-only role that sees only views of one school (schema `soporte_<abr>`, `WHERE plantel LIKE '<code>.%'`) on the Aurora reader. The filler adds the per-user filter on top. EDW reaches Aurora over the peering: Aurora's SG gets inbound 5432 from EDW. That's a production change; ask first.
5. **PHP:** foot.inc emits the signed token for the logged-in user (snippet from the identity work).
